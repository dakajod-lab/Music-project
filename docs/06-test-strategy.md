# 06 — Test Strategy

_Status: **Agreed v1.0** (2026-10-06)._

## 1. Purpose
This strategy describes **how** we gain confidence that the app meets its requirements
([features](../features)), its NFRs ([04-nfr.md](04-nfr.md)) and handles its risks ([04b-risk-register.md](04b-risk-register.md)).
It supports the quality goals Q1–Q4 in the [business case](01-business-case.md).

## 2. Principles
| # | Principle | Agreed |
|---|-----------|--------|
| P1 | Requirements are Gherkin feature files and run as tests (living documentation). | 2026-10-01 |
| P2 | Test effort follows the risk score. | 2026-10-01 |
| P3 | No manual steps without a clear pass/fail. Subjective areas use exploratory charters with concrete observations. | 2026-10-05 |
| P4 | Automate the app's *reaction* to device events; check on the real device that the device *really sends* those events. | 2026-10-05 |
| P5 | Big acceptance test first, then trust the automation (see §8). | 2026-10-05 |
| P6 | Every bug gets an automated regression test before it is closed. | 2026-10-06 |
| P7 | A flaky test is a **signal to investigate**, never something to re-run until green. See §12. | 2026-10-06 |
| P8 | Coverage and mutation score are **information, not targets**. No fixed thresholds. See §7. | 2026-10-06 |

## 3. Test levels
| Level | What | Tool | Runs | Location |
|-------|------|------|------|----------|
| Static | Types, lint rules, formatting | TypeScript (strict), ESLint, Prettier | Every commit | — |
| Unit | Core: rules, state machine, WAV encoder, clipping detection | Vitest | Every commit | `src/**/*.test.ts` next to the code |
| Integration | Core + fake adapters: full flows without a browser | Vitest | Every commit | `tests/integration/` |
| Component | React components in isolation | Vitest + React Testing Library | Every commit | `src/**/*.test.tsx` |
| Adapter | Real browser APIs behave as assumed | Vitest browser mode (Chromium) | Every PR | `tests/adapters/` |
| Acceptance (E2E) | All non-manual scenarios in `/features` against the built app, fake microphone | playwright-bdd | Every PR | `features/` + `tests/steps/` |
| Accessibility | WCAG 2.2 AA violations | axe-core inside acceptance tests | Every PR | — |
| Exploratory | Real devices, sound, assumptions | Charters in `docs/charters/` | Per §8 | — |

## 4. Test techniques (and where we use them)
| Technique | Example in this project |
|-----------|-------------------------|
| **Equivalence partitioning** | Input levels: silence / normal / clipping (REC-005) |
| **Boundary value analysis** | Time limit: 0 s, 1 s, 4:59, 5:00, 5:01 (REC-002) |
| **State transition testing** | Recorder state machine: every state × event, including invalid ones (ADR-007) |
| **Decision tables** | Noise filter on/off × which browser processing is enabled (R2) |
| **Round-trip testing** | Record → store → reload → export → parse; samples must be identical (R5, STO-001) |
| **Fault injection** | Crash, freeze, mic `ended`, storage quota (R3, R4, R12) |
| **Exploratory testing** | Charters CH-001 (audio processing), CH-002 (phone interruptions), … |

## 5. Test data
Deterministic audio files, **generated by a script** (not recorded), stored in `tests/fixtures/audio/`:

| File | Content | Used for |
|------|---------|----------|
| `silence.wav` | 2 s of silence | Level meter, no clipping |
| `sine-440-normal.wav` | 440 Hz at −12 dBFS | Normal recording, round-trip comparison |
| `sine-440-clipped.wav` | 440 Hz at full scale, flattened peaks | Clipping detection (REC-005.2) |
| `click-120bpm.wav` | Clicks at exact sample positions | Alignment / latency (R1, 0.2) |

Because the files are generated, the expected values (peak, length, click positions) are known exactly.

## 6. Traceability
- Acceptance scenarios carry their ID in the name (`REC-001.2`).
- Unit/integration tests reference the requirement or risk they support in the `describe` name
  (e.g. `describe('REC-002 time limit', …)`).
- CI produces a **traceability report**: every scenario ID → test result. A scenario without an
  automated test (and without `@manual`) fails the build.

## 7. Quality gates (CI, every pull request)
A pull request can only be merged when all gates pass.

| Gate | Threshold |
|------|-----------|
| Type check + lint | 0 errors |
| Unit / integration / component tests | 100 % pass |
| Line + branch coverage on **Core** | **Reported only** (P8) |
| Acceptance tests, Tier 1 (Chromium desktop + Android phone emulation) | 100 % pass |
| Acceptance tests, Tier 2 (Firefox, WebKit) | Reported, **not blocking** (NFR-CMP-003) |
| Accessibility (axe) | 0 serious / critical violations |
| Traceability | Every non-manual scenario has a passing test |
| Dependencies | 0 high / critical vulnerabilities (`npm audit`) |
| **Mutation score** on Core (Stryker) | **Reported only** (P8) |

**Why coverage and mutation score are not gates (P8):** a fixed percentage invites tests that exist only to
reach the number and add no value. Coverage only shows that code *ran*. Instead:
- Both numbers are shown on every pull request, so changes in trend are visible in review.
- **Low** coverage is used as a pointer: "this area is untested, is that a risk?" **High** coverage proves little.
- Surviving mutants (Stryker) are reviewed: each one is either a missing test that matters, or accepted on purpose.
- **Equivalent mutants** (a change that cannot alter behaviour) are documented with a code comment, but **not**
  switched off with `// Stryker disable`: that switches off *every* mutant of that kind on the line, including real ones.
  They stay visible as survivors in the nightly report.

## 8. Release testing (P5)
1. **Impact analysis** per release: which features, adapters and platform versions changed? (checklist in the PR template)
2. **First release of a big feature:** all automated tests + full exploratory session with all relevant charters on the reference devices.
3. **Later releases:** automated tests only, plus charters the impact analysis points to.
4. Manual `@manual` scenarios (e.g. EXP-001.3 Ableton import) are run when the impact analysis requires them.

## 9. Defect management
- Bugs are **GitHub Issues** with a template: steps, expected, actual, device/browser, build, linked requirement/risk.
- **Severity:** S1 idea lost / app unusable · S2 feature broken · S3 workaround exists · S4 cosmetic.
- S1/S2 block a release.
- Closing a bug requires a linked regression test (P6).

## 10. Definition of Done (for a user story)
- [ ] Acceptance scenarios agreed and in `/features`
- [ ] Code + unit/integration tests written; all quality gates pass
- [ ] Code reviewed (pull request)
- [ ] Deployed to GitHub Pages
- [ ] Charters run if this is the first release of the feature (P5)

## 11. Metrics we track
Requirement coverage · mutation score · coverage on Core · open bugs per severity · bugs found by level
(unit / acceptance / exploratory / production) · flaky test count.

## 12. Flaky tests (P7)
A flaky test passes and fails on the same code. The flakiness itself tells us something, so it is investigated, not hidden.

1. **Record it:** a GitHub Issue with label `flaky`, including failing runs and logs.
2. **Find the root cause.** It is one of three kinds:

| Root cause | Example | Action |
|------------|---------|--------|
| **The test is badly written** | Waits a fixed 500 ms instead of waiting for a state | Fix the test |
| **The test approach is wrong** | Timing measured in a real browser on a busy CI machine; a level that cannot be deterministic | Redesign: lower test level, fake clock, different technique |
| **The product has a real bug** | A race condition between saving a chunk and stopping a recording | Fix the product: a normal bug with severity (P6) |

In an audio/timing app the third kind is especially likely and important (R1, R4), so it is checked first, not last.

3. **Automatic retries never hide flakiness:** CI may retry a failed test once, but a test that only passes on retry
   is reported and tagged as flaky. The retries give *more data* about when and how often it fails.
4. **Quarantine** (temporarily excluding the test from the gate) is only allowed with a linked issue and only while
   the root cause is being investigated. **Deleting** a test is only allowed when what it checks is covered elsewhere.
